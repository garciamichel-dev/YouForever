# YouForever V5.3.2 — Despliegue seguro de Firestore privado

Este procedimiento migra el servidor al Firebase Admin SDK y cierra las reglas públicas de Firestore
sin interrumpir el servicio. **Nada de esto se ha aplicado a producción.** Cada paso lo ejecuta una
persona con permisos sobre el proyecto, en el orden indicado.

Valores de este proyecto (de `firebase-applet-config.json`):

| Dato | Valor |
| --- | --- |
| Proyecto Firebase | `balmy-smile-fc70r` |
| Base de datos (con nombre) | `ai-studio-24473850-0d4d-4247-8313-c0172221b6cb` |

En los comandos: `PROJECT=balmy-smile-fc70r`, `DB=ai-studio-24473850-0d4d-4247-8313-c0172221b6cb`,
`SERVICE` = servicio de Cloud Run, `REGION` = su región, `BUCKET` = un bucket de respaldo privado.

## 0. Requisito previo: controlar la identidad del servicio

El servidor V5.3.2 se autentica con la cuenta de servicio adjunta a Cloud Run (Application Default
Credentials). Comprueba cuál es y que puedes concederle permisos:

```bash
gcloud run services describe "$SERVICE" --region "$REGION" --project "$PROJECT" \
  --format='value(spec.template.spec.serviceAccountName)'
```

Si el servicio lo gestiona Google AI Studio y no puedes ver o cambiar su cuenta de servicio ni su
proyecto, primero despliega la aplicación en un Cloud Run propio (por ejemplo, exportando el código y
`gcloud run deploy`). Sin una identidad controlable no se pueden cerrar las reglas.

## 1. Respaldo verificable

```bash
gcloud firestore export "gs://$BUCKET/youforever-$(date +%Y%m%d-%H%M)" \
  --database="$DB" --project="$PROJECT"
gcloud firestore operations list --database="$DB" --project="$PROJECT"   # debe terminar en SUCCESSFUL
```

Verificación: importa el respaldo en una base de datos aislada y cuenta documentos de
`interviews`, `answers` y `participantBookVersions`:

```bash
gcloud firestore databases create --database=yf-restore-check --location=<misma-ubicación> --project="$PROJECT"
gcloud firestore import "gs://$BUCKET/<carpeta-del-respaldo>" --database=yf-restore-check --project="$PROJECT"
```

Recomendado: activar la recuperación a un punto en el tiempo (PITR) en la base de producción. Como
las reglas anteriores permitían escrituras públicas, revisa también en el respaldo que no haya
documentos ajenos (por ejemplo, en `admins`, que el servidor no usa).

## 2. Identidad de servicio e IAM (mínimos privilegios)

Crea una cuenta dedicada y concédele solo acceso de datos a ESTA base de datos:

```bash
gcloud iam service-accounts create youforever-server --project="$PROJECT"
SA="youforever-server@$PROJECT.iam.gserviceaccount.com"

gcloud projects add-iam-policy-binding "$PROJECT" \
  --member="serviceAccount:$SA" --role="roles/datastore.user" \
  --condition="expression=resource.name==\"projects/$PROJECT/databases/$DB\",title=youforever-db-only"
```

- `roles/datastore.user` permite leer y escribir documentos, sin administrar índices, reglas, bases
  de datos ni IAM. No concedas `Owner`, `Editor` ni `Firebase Admin`.
- Si Cloud Run está en otro proyecto, concede el rol en `balmy-smile-fc70r` a la cuenta de ese
  servicio.
- No crees ni descargues claves JSON. En una estación de trabajo usa
  `gcloud auth application-default login` con un usuario autorizado.
- La verificación de los tokens de administrador solo descarga certificados públicos de Google y no
  necesita IAM.

Adjunta la cuenta al servicio (en el siguiente despliegue):

```bash
gcloud run services update "$SERVICE" --region "$REGION" --project "$PROJECT" --service-account="$SA"
```

## 3. Migración del servidor (reglas antiguas todavía activas)

Despliega V5.3.2 **sin tocar todavía las reglas**. El Admin SDK no depende de ellas, así que el
servidor funciona igual con las reglas antiguas y con las nuevas, y este paso es reversible.

Variables de entorno de Cloud Run:

| Variable | Valor | Uso |
| --- | --- | --- |
| `ADMIN_SESSION_SECRET` | ≥ 32 caracteres aleatorios (Secret Manager) | Firma las cookies de administrador y de medios |
| `FIREBASE_PROJECT_ID` | (opcional) | Solo si el proyecto no es el del archivo de configuración |
| `FIRESTORE_DATABASE_ID` | (opcional) | Solo para un entorno de pruebas con otra base |

No definas `FIRESTORE_EMULATOR_HOST` en producción.

Al instalar dependencias: el proyecto ya tenía un conflicto de dependencias pares (vite) anterior a
V5.3.2. Instala como hasta ahora (si `npm install` falla por ese conflicto, usa `--legacy-peer-deps`).

Comprobaciones en los registros tras el despliegue: no hay errores `permission-denied` ni
`unauthenticated` de Firestore, el panel de administración carga las entrevistas, un participante
abre su historia y se ven fotos y audios.

## 4. Pruebas en un entorno aislado

1. Crea una base de datos de pruebas (`gcloud firestore databases create --database=yf-staging …`)
   o usa un proyecto Firebase de pruebas, e importa en ella el respaldo del paso 1.
2. Despliega una revisión de Cloud Run sin tráfico (`--no-traffic --tag=staging`) con
   `FIRESTORE_DATABASE_ID=yf-staging`.
3. En una estación con Java ejecuta `npm run test:rules`. Usa el emulador oficial de Firebase y
   prueba las reglas nuevas.
4. Ejecuta `npm test`, que incluye las pruebas del servidor contra un emulador de Firestore.

## 5. Verificar que el servidor funciona sin reglas públicas (en el entorno aislado)

Despliega las reglas nuevas solo en la base de pruebas. Para ello cambia temporalmente `database`
en `firebase.json` a `yf-staging`, o usa una copia del archivo:

```bash
firebase deploy --only firestore:rules --project "$PROJECT"
```

Recorrido de humo sobre la revisión `staging`:

- Inicio de sesión de administrador.
- Crear una entrevista.
- Responder como participante, con foto y audio.
- Generar la vista previa y el libro.
- Guardar el libro y exportar el PDF.
- Ver el informe de auditoría.
- Mi Esencia: abrir el panel y una conversación.
- Reiniciar la revisión (desplegarla de nuevo) y comprobar que todo sigue ahí.

Verifica que un cliente público queda bloqueado (debe responder 403 o PERMISSION_DENIED):

```bash
curl -s "https://firestore.googleapis.com/v1/projects/$PROJECT/databases/yf-staging/documents/interviews?pageSize=1"
```

## 6. Actualización controlada de las reglas en producción

Solo cuando los pasos 3 a 5 estén verificados, y en un horario de poco uso:

```bash
git show 8de522b:firestore.rules > firestore.rules.previous   # reglas anteriores, para revertir
firebase deploy --only firestore:rules --project "$PROJECT"     # firebase.json apunta a la base con nombre
```

## 7. Pruebas posteriores

- El `curl` del paso 5 contra la base de producción devuelve 403 o PERMISSION_DENIED.
- Repite el recorrido de humo en producción con una entrevista de prueba.
- Reinicia el servicio y confirma que se recuperan las versiones y los informes, y que la cuota no
  cambia.
- Revisa los registros 24 h: no deben aparecer errores `permission-denied` del servidor.

## 8. Plan de reversión

| Fallo | Acción |
| --- | --- |
| El servidor V5.3.2 no accede a Firestore (IAM) | Revisa la cuenta y el rol del paso 2. Si urge, redirige el tráfico a la revisión anterior: `gcloud run services update-traffic "$SERVICE" --to-revisions=<anterior>=100`. Las reglas siguen siendo las antiguas. |
| Algo falla tras cerrar las reglas | 1) Publica de nuevo las reglas anteriores: `cp firestore.rules.previous firestore.rules && firebase deploy --only firestore:rules`. 2) Si hace falta, vuelve a la revisión anterior del servidor. **Orden:** primero las reglas, porque el servidor anterior (SDK de cliente) necesita las reglas públicas. |
| Datos dañados | Importa el respaldo del paso 1 (`gcloud firestore import … --database="$DB"`) o usa PITR. |

Volver a las reglas públicas reabre la vulnerabilidad; hazlo solo de forma temporal.

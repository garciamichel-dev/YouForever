# V5.6.2 — Seguridad de accesos

Corrige cuatro hallazgos de la revisión de seguridad sin cambiar cómo entran los participantes ni la familia.

## Qué cambia

| # | Antes | Ahora |
|---|---|---|
| 1 | Además del código y el enlace, daban acceso: el ID de la entrevista (incluido en cada ID de foto y audio), el ID del participante, el ID del token, el hash guardado y códigos YF/LEG calculados desde esos IDs. | Solo da acceso el **código guardado** del token (en cualquier formato: minúsculas, sin guion, solo el sufijo, pegado de WhatsApp o en URL), su código heredado guardado y el **enlace real**. Un token antiguo sin código guardado sigue entrando con el código que siempre mostró el panel. |
| 2 | Al revocar un token, la autorreparación creaba otro válido en la siguiente solicitud. | La revocación es definitiva. Para devolver el acceso existe `POST /api/tokens/reactivate` (admin), que conserva el mismo código y enlace. La autorreparación sigue creando un token para participantes que no tienen ninguno. |
| 5 | Solo `/participant/session` y `/mi-esencia/family/verify-code` contaban intentos; acertar borraba los fallos; la IP no se resolvía detrás del proxy. | Un único limitador cubre todas las rutas `/participant/*` y `/mi-esencia/family/*`. Solo cuentan códigos que no existen (uno vencido o revocado nunca cuenta). Acertar no borra los fallos. Durante un bloqueo, quien ya entró desde esa dirección sigue entrando. `trust proxy` = 1 salto (Cloud Run). |
| 7 | Las historias de prueba se sembraban en cada arranque, también en producción, con códigos públicos (`SAN-7841`, `CAR-4923`…), y reaparecían al borrarlas. | No se siembran solas en producción; el botón del panel las crea cuando se necesiten. Cada siembra asigna enlace y código **aleatorios** (el panel los muestra) y los anteriores dejan de funcionar. Regeneraciones forzadas del libro: máximo 15 al día por entrevista para participantes (el administrador está exento); por encima se reutiliza el resultado vigente, sin mostrar error. |

## Variables de entorno (todas opcionales)

| Variable | Valor por defecto | Uso |
|---|---|---|
| `YF_LEGACY_DERIVED_ACCESS_CODES` | apagado | `1` = palanca de emergencia: vuelve a aceptar códigos calculados (nunca IDs ni hash). Solo si un participante real resultara depender de uno. |
| `TRUST_PROXY_HOPS` | `1` | Saltos de proxy de confianza para la IP real. `0` lo desactiva. |
| `YF_SEED_TEST_STORIES` | automático | `1` siempre siembra al arrancar, `0` nunca. Sin valor: solo fuera de producción (`NODE_ENV=production` o Cloud Run). |
| `BOOK_FORCE_REFRESH_DAILY_LIMIT` | `15` | Regeneraciones forzadas por entrevista cada 24 h para participantes. `0` = sin límite. |

## Antes y después de desplegar

1. Con sesión de administrador, abrir `GET /api/admin/access-codes/report`. Solo devuelve conteos e IDs, nunca códigos.
   - `tokensWithoutStoredCode`: tokens antiguos que entran con el código que muestra el panel (siguen funcionando).
   - `predictableCodes`: tokens cuyo código se puede calcular a partir del ID del participante. Siguen funcionando; rotarlos es un paso posterior (requiere reenviar el código al participante).
   - `participantsWithAllTokensRevoked`: participantes que ya no pueden entrar (antes sí podían, por el problema #2).
2. Si en producción usas las historias de prueba, créalas con el botón del panel y toma los códigos nuevos de ahí.
